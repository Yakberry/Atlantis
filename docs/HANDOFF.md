## 1. Проект и стиль работы

Пошаговая (одновременные ходы) мультиплеерная стратегия на гексагональной карте-острове. Сейчас: лобби, комнаты, чат,
карта с туманом войны, юниты и колонии, добыча ресурсов. Автор — разработчик из геймдева; хочет **чистую файловую структуру
и лаконичный код** уровня «10 лет в геймдеве».

Договорённости:
- Общаемся **по-русски**; комментарии в коде и тексты интерфейса тоже по-русски, идентификаторы по-английски.
- Код короткий, без лишних абстракций и «на вырост». Комментарий объясняет *почему*, а не *что*.
- Claude **не может запускать приложение** (в песочнице нет сети, `npm install` недоступен). Есть `node` и глобальный `tsc`:
  чистую логику (`shared/src/game`) проверяем компиляцией и smoke-тестом (рецепт в п. 8). Vue/сервер/БД автор проверяет сам.
- Изменения отдаются **zip-архивом только с изменёнными файлами** (пути от корня: `packages/...`). Автор распаковывает:
  `unzip -o <архив> -d /Users/uzer/WebstormProjects/AtlantisProject`, затем `git status` для проверки.
  **Удаления и переименования архив не выполняет** — их нужно перечислять отдельно.
- Каждую итерацию автор подтверждает фразой «всё работает». Последние шаги (фазы хода, строительство и дороги, названия локаций) **ещё не подтверждены**;
  автору нужно вручную удалить `assets/sprites/tiles/gold.png` и `assets/sprites/resources/gold.svg`.

## 2. Стек и запуск

Node ≥ 20.12, npm workspaces, TypeScript (strict, `noUncheckedIndexedAccess`, `verbatimModuleSyntax` → везде `import type`),
Vue 3 + Pinia 2 + Vue Router 4 + Vite 6, Fastify 5 + Socket.IO 4 + `pg`, zod 3, PostgreSQL 17 (docker-compose).

```bash
npm install
npm run db:up      # Postgres в Docker (atlantis/atlantis/atlantis)
npm run dev        # сервер :3000 + клиент :5173 (Vite проксирует /api и /socket.io, host: true для локальной сети)
npm run typecheck
```

`.env` необязателен (`PORT`, `HOST`, `DATABASE_URL` имеют значения по умолчанию). Миграции применяются при старте сервера.

## 3. Архитектура и принципы

1. **Сервер авторитарен.** Клиент шлёт намерения (`move`, `harvest`, `drop_unsupplied`, `build`, `end_phase`), сервер проверяет и применяет.
2. **Правила игры — чистые функции без IO** в `packages/shared/src/game`, общие для клиента и сервера.
   Случайность подаётся параметром `rng` (по умолчанию `Math.random`) → тесты воспроизводимы.
3. **Туман войны считает сервер.** Клиент получает не полное `GameState`, а персональную проекцию `GameView`
   (`viewFor(state, viewerId)`). Рассылка: `broadcast()` в `transport/socket.ts` шлёт каждому сокету комнаты его снимок.
   Любое новое поле состояния нужно сначала продумать с точки зрения «что видит игрок».
4. **БД — источник истины.** Каждое действие выполняется в транзакции с `SELECT … FOR UPDATE` по строке комнаты;
   игроки действуют одновременно, блокировка сериализует их. Состояние партии лежит в `rooms.game` (jsonb).
5. **Слои сервера:** `transport` (приём, zod-валидация, рассылка) → `modules/*/service` (сценарии, транзакции) → `repository` (SQL).
6. **Протокол типизирован в одном месте** (`shared/protocol.ts` + `schemas.ts`); ответы — `Ack<T>` = `{ok:true,data}|{ok:false,error}`.
7. **Ожидаемые ошибки** — `AppError` (текст безопасен для игрока); остальное логируется и превращается в «Внутренняя ошибка».
8. **События и отчёты.** `applyAction` возвращает `Result<{state, events, reports}>`. `events` (например, `harvested`) уходят только
   совершившему действие. `reports` (бои, осады, потери без снабжения) — сообщения чата с `audience`: их получают участники и те, кто
   видит локацию (фильтрация в БД через `messages.audience` и при рассылке в `emitMessage`). Текст отчёта формирует сервер (`room.reports.ts`).

## 5. Правила игры (как реализовано сейчас)

- **Игроки:** 1–4 (одиночный запуск разрешён для отладки). Хост до старта задаёт число клеток суши `mapSize` (5–35) и тип карты `mapStyle`.
- **Карта:** `mapSize` клеток суши + море вокруг (гекс по контуру и во внутренних заливах); поле всегда единое. Ресурс клетки суши
  случайный: food, wood, marble, copper. Режимы суши (`MAP_STYLES`, по умолчанию `solid`), везде рост кластера от центра:
  `classic` — клетки с меньшим числом соседей выбираются охотнее (тонкие отростки, исходное поведение);
  `solid` — охотнее клетки с большим числом соседей + `removeSpurs` (клетки с ≤1 соседом переносятся): отростков нет;
  `islands` — материк в стиле `solid` + острова по 2–5 клеток (~30% суши, но материку остаётся ≥ `MAX_PLAYERS`),
  каждый остров на расстоянии 2–3 клеток от остальной суши (не касается её, а море вокруг смыкается).
- **Названия:** каждой клетке суши на старте случайно и без повторов достаётся название из `LOCATION_NAMES` (пока «1»…«35»; у моря названия
  нет). Название видно, пока локация видна; на плитке — первой строкой, ресурсом — второй. В чате локации указываются названиями.
- **Старт:** у каждого игрока своя случайная, отличная от других, клетка **материка**: колония + 2 юнита (на острове игрок был бы
  заперт: кораблей ещё нет).
- **Видимость построек:** `Unit.fresh` / `Road.fresh` (построено в эту фазу, скрыто от других), `Unit.shownKind` (вид для других). Флаги снимаются при переходе
  строительство → добыча (`advance` в `phases.ts`); фильтрация — в `viewFor`.
- **Виды (`UNIT_KINDS`):** `unit` (обзор 2, ходит по суше), `colony` и `fortified_colony` (обзор 1, не ходят, добывают, `colony: true`).
  Все — «юниты» в широком смысле: принадлежат игроку, занимают клетку, участвуют в споре за неё. Свойства-таблица: `supply`, `siegeHit` и др.
- **Ход = фазы** (`Phase`: maneuver → supply → build → harvest, затем автоматический бой). Фаза идёт, пока не готовы все игроки;
  игрок, которому в фазе нечего делать, готов сам (`autoReady` в `phases.ts`). `ready` — готовые в текущей фазе. `settle()` после каждого
  действия двигает ход вперёд сколько можно (цепочка может пройти несколько фаз сразу).
  1. **Манёвр:** `move` юнитом в соседнюю клетку суши. Один шаг за ход; если юнит хоть раз прошёл по дороге (любого игрока) — ещё один
     (всего два). Для владельца ход действует мгновенно, остальные видят его после конца манёвра (`revealed`). Если юниты разных игроков
     должны поменяться местами (старт↔финиш), все они случайно оказываются в одной из двух локаций (`resolveManeuver`).
  2. **Снабжение:** `UNIT_KINDS[kind].supply` (юнит: 1 еда + 1 медь, колония и укреплённая: 1 еда). Кому хватает, тому списывается
     автоматически; в чат уходит запись журнала снабжения на каждого игрока (видна всем: запасы и так публичны после фазы). Кому не хватает,
     тот выбирает (`drop_unsupplied`), кто остаётся без снабжения: допустим только минимальный набор отказов (`isValidDrop`), выбранные
     удаляются. `GameView.supply` — текущая потребность (в баре ресурсов в скобках).
  3. **Строительство:** `build {building, at, to?}`. Место (`canBuildAt`): суша, **разведана**, не спорная и не захвачена другим игроком;
     либо в ней стоят только свои юниты/постройки, либо она пуста и соседствует только с колониями этого игрока. Постройки (`BUILDINGS`):
     колония (1 лес + 1 мрамор, не больше одной на локацию), укреплённая колония (1 лес + 3 мрамора, только поверх своей обычной колонии,
     заменяет её, осада уничтожает её лишь от 5), дорога (1 мрамор, между двумя соседними локациями: `at` + `to`; **оба конца должны быть местами, доступными игроку для
     строительства**, дороги там ещё нет; дороги общие). Новые постройки и дороги скрыты от других игроков до конца фазы строительства
     (`fresh`); улучшение колонии до тех пор выглядит для них обычной колонией (`shownKind`). Фаза пропускается, если игрок ничего не может построить (`canBuildAnything`). `GameView.sites` — места для строительства.
  4. **Добыча:** `harvest` по колонии или `end_phase` («Завершить ход»). Колония «захвачена», если в её локации стоят чужие юниты
     (`isCaptured`) — не добывает. **За фазу добывают только с одной цепочки колоний** (`colonyChains`: колонии, соединённые
     дорогами; дороги **общие**, годятся дороги любого игрока); автодобыча берёт ту же, с которой уже добывали, иначе наибольшую
     (по числу колоний, способных добывать). Добыча 1–3 ед. ресурса локации.
  5. **Бой** (сразу после добычи, без действий игроков): в спорной локации (сущности ≥2 игроков) юниты ≥2 игроков → каждый бросает d6,
     побеждает игрок с наивысшим одиночным броском и уничтожает юнитов остальных; наивысший у ≥2 игроков → ничья. Юниты одного игрока
     против вражеской постройки → осада: бросок d6 ≥ `siegeHit` постройки (колония 4, укреплённая 5) у любого уничтожает её, иначе гибнет
     случайный нападающий. Постройки кубик не бросают; колония проигравшего в бою в тот же ход не осаждается. Результаты — в чат (`audience`).
  Запасы: старт `START_STOCK` = 4 еды, 2 леса, 4 мрамора, 4 меди. Запас игрока виден остальным (`GameView.rivals`), но обновляется
  только после каждой фазы (`shownStock`), свой — актуальный. Победа также при уничтожении всех сущностей, кроме одного игрока.
- **Видимость:** клетку видит владелец, у которого сущность в пределах её обзора. Свои сущности — по реальным позициям (мгновенно),
  чужие — по позициям на момент последнего раскрытия манёвра (`revealed`). Ресурс суши известен, если клетка «изведана» (там кто-то
  побывал к последнему раскрытию) или там сейчас стоит свой. **Море видно как море сразу.** Скрыто: чужая усталость, актуальный чужой запас (виден только снимок после фазы).
  Координаты скрытых клеток публичны (форма карты известна), содержимое — нет.
- **Принадлежность клетки:** один владелец → граница его цвета; несколько → «спорная» (жёлтая пунктирная); пусто → бледная.
- **Победа — заглушка:** `WIN_TURN = 3`, побеждает первый игрок из `playerOrder`. Для отладки значение стоит поднять.
- **Выход из комнаты:** игрок удаляется (его юниты и запас — тоже), в чат пишется «Игрок X отключился», хост переходит
  к раннему участнику, пустая комната удаляется из БД, в партии остался один игрок → он побеждает.

## 6. Протокол и БД

**Клиент → сервер** (все с `Ack`, кроме `room:detach`): `room:create`, `room:join {roomId}` → `{room, history}`,
`room:leave {roomId}` (выход насовсем), `room:detach` (закрыл экран, остался участником), `room:configure {roomId, mapSize, mapStyle}`,
`game:start {roomId}`, `game:action {roomId, action}` (`move` / `harvest` / `drop_unsupplied` / `build` / `end_phase`) → `GameEvent[]`, `chat:send {roomId, text}`.
**Сервер → клиент:** `room:updated(RoomSnapshot)` (персональный), `chat:message`.
Авторизация: `POST /api/session {name}` → `{token, player}`; токен уходит в `socket.handshake.auth.token`. Коды комнат — 5 символов без I/O/0/1.

**Таблицы:** `players`, `rooms (id, host_id, status, map_size, game jsonb)`, `room_members`, `messages (…, system bool, player_id null для служебных, audience uuid[])`.
**Миграции:** 001 схема, 002 системные сообщения, 005 `map_size`, 009 `map_style` + лимит `map_size` до 35, 011 `messages.audience`; 003/004/006/007/008/010/012/013 — «сброс»
(`delete from rooms where game is not null`).
**Правило:** при несовместимом изменении `GameState` добавлять миграцию-сброс; сохранённые партии старого формата ломают `viewFor`.

## 7. Клиент: что важно знать

- **HexBoard** — SVG: гексы, юниты, подсветка, всплывающие цифры. Выбор: клик по своему юниту → клик по подсвеченной соседней
  клетке (только на фазе манёвра); клик по своей неиспользованной колонии на фазе добычи = добыча. Не использовавшие действие
  сущности подсвечены кольцом. На фазе снабжения при нехватке ресурсов клик по своей сущности помечает её «без снабжения»
  (`picking`/`unsupplied` в `GameBoard` → `HexBoard`), подтверждение отправляет `drop_unsupplied`. Захваченные колонии — красный пунктир.
  `PhaseBar` показывает ход и фазы, `ResourceBar` — запас и `(нужно на снабжение)`, `PlayerList` — запасы соперников и «готов».
- **usePanZoom** держит центр и масштаб, `viewBox` подгоняется под пропорции контейнера. `setPointerCapture` включается только после
  порога перетаскивания, иначе ломаются клики.
- **Спрайты:** `board/sprites.ts` находит файлы через `import.meta.glob` и проверяет загрузку через `Image.onload`. Пустой/битый/
  отсутствующий файл → запасной вариант (заливка, фигуры, цветные квадраты). Иконки юнитов красятся в цвет игрока SVG-фильтром
  (`feFlood` + `feComposite` по альфа-каналу), поэтому в файле цвет значения не имеет.
- **Настройки** (`stores/settings`, `localStorage`): «Упрощённая графика локаций» отключает картинки локаций, остаётся заливка.
- Экран комнаты — на всю ширину и ровно `100dvh`; мобильную версию пока не рассматриваем.
- Цвета: игроки — `['#ff3b4e','#19d3ff','#b06bff','#ff9e2c']` (по `slots`), ресурсы и море — в `board/palette.ts`.

## 8. Рецепты

**Проверка логики без сети** (из корня репозитория, адаптировать пути):
```bash
tsc -p /tmp/smoke/tsconfig.json   # extends tsconfig.base.json, noEmit:false, outDir:/tmp/smoke/out, rootDir:packages/shared/src/game
cd /tmp/smoke/out && echo '{"type":"module"}' > package.json && sed -i -E "s#from '(\./[a-z]+)'#from '\1.js'#g" *.js
node test.mjs   # свои проверки: createGame/applyAction/viewFor на сотнях партий с детерминированным rng
```
Что стоит проверять всегда: приватность (проекция соперника не меняется от чужого хода до раскрытия), границы случайных величин,
связность и замкнутость карты. **В репозитории автотестов пока нет** (см. бэклог).

**Новая сущность/механика:** 1) типы и константы в `model.ts` (`UNIT_KINDS` — таблица свойств видов), 2) правило в `rules.ts`,
3) проекция в `visibility.ts`, 4) схема в `schemas.ts` + протокол, 5) клиент, 6) миграция-сброс при смене формата.

## 9. Решения, статус и бэклог

**Принятые решения (не переоткрывать без причины):** старт на разных клетках материка; тип карты по умолчанию `solid` (в `classic` тонкие
отростки были частой жалобой); острова пока недостижимы (ждут кораблей); один гекс моря по контуру + заливы; суша
скрывает ресурс до посещения, море нет; спорная граница жёлтая (белая терялась на мраморе); запас ресурсов приватен;
положение чужих юнитов обновляется только при раскрытии манёвра; тоггл упрощённой графики влияет только на локации;
ресурсы: еда, лес, мрамор, медь (медь заменила железо); новые постройки и дороги других игроков видны только после конца фазы строительства, запас — приватный до конца фазы; дороги общие (движение и цепочки), рисуются прямоугольником на общей грани; строительные правила проверяются по истинному состоянию (ошибка места общая, чтобы не раскрывать туман);
ничья в бою, если наивысший бросок у ≥2 игроков; осада колонии проигравшего начнётся только в следующий ход; результаты боёв в чате видят
только участники и те, кто видит локацию; фаза добычи без колоний, способных добывать, завершается сама; поражение — потеря всех сущностей.

**Бэклог / идеи (по убыванию очевидности):**
0. **Не сделано (ждёт решения пользователя):** трёхэтапный манёвр (всадники → по дорогам → марш) с синхронизацией после каждого этапа, юнит «всадник»
   вместо одного из стартовых юнитов, блокировка столкнувшихся юнитов до конца хода, встречное движение между этапами. Сейчас манёвр одноэтапный:
   один шаг, второй шаг, если юнит прошёл по дороге.
0. Названия локаций: пользователь заполняет `names.ts` своими (уникальными!) строками.
1. **Корабли:** вид `ship` с `terrain: 'sea'` в `UNIT_KINDS`, постройка за ресурсы, перевозка юнитов (море и острова уже есть; после
   появления кораблей можно разрешить старт и на островах).
2. Трата ресурсов (постройка юнитов/колоний), цели и настоящее условие победы вместо `WIN_TURN = 3` (сейчас игра длится 2 хода).
3. Расширение боёв: характеристики видов (сила, броня), отступление, боевые отчёты на карте (вспышка на клетке), имена локаций.
4. Автотесты в репозитории (vitest для `shared/game`: перенести smoke-проверки).
5. Разворачивание на сервере: раздача `client/dist` через Fastify, CORS/домен, Dockerfile, `tsup`-сборка сервера (миграции читаются из `./migrations` относительно cwd).
6. Индикатор «игрок отключился» (presence), список комнат/очистка заброшенных, настоящая авторизация, «память» разведанных клеток (сейчас вне поля зрения клетка снова серая).
7. Подключить готовые спрайты (файлы-заготовки уже на месте), при необходимости применить упрощённый режим и к юнитам/иконкам.

**Известные нюансы:** клик по колонии при выбранном юните приоритетно добывает (чтобы зайти в её клетку — кликайте мимо домика);
заготовка `tiles/sea.png` используется, `unexplored.png` — только для неизведанной суши.
