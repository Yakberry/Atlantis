# Развёртывание Atlantis

Один процесс Node (Fastify + Socket.IO) раздаёт и клиент, и игру; состояние партий лежит в Postgres.
Локальный запуск для отладки остаётся таким же простым, а на хостинге нужны только Node/Docker и база.

## Режимы запуска

| Режим | Команды | Адрес |
|---|---|---|
| **Разработка** (как раньше) | `docker compose up -d` (база), `npm run dev` | клиент http://localhost:5173, сервер :3000 |
| **«Боевой» режим на своей машине** | `docker compose up -d`, `npm run start:local` | всё на http://localhost:3000 |
| **Всё в Docker на своей машине** | `docker compose -f docker-compose.prod.yml up --build -d` | http://localhost:3000 |
| **Хостинг** | образ из `Dockerfile` или `npm ci && npm run build`, запуск `npm run start` | адрес хостинга |

После `npm install` появились две новые зависимости сервера (`@fastify/static`, `@fastify/compress`): выполните `npm install` и `npm run typecheck`.

### Запасной план, если сервер подвёл
Запустите режим «боевой на своей машине» (или Docker-вариант) и пригласите друзей:
- в одной сети: `http://<ваш-IP>:3000`;
- через интернет: один туннель на порт 3000 (Cloudflare Tunnel, ngrok, Tailscale Funnel). Клиент и сервер на одном адресе, поэтому достаточно одного туннеля.

Партии при этом лежат в вашей локальной базе, отдельно от серверной.

## Требования к хостингу
- **Постоянный процесс или контейнер с поддержкой WebSocket** (не «serverless» с лимитом времени запроса).
- **Один экземпляр.** Socket.IO держит соединения в памяти процесса: несколько экземпляров потребовали бы Redis-адаптера и «липких» сессий (не сделано, для целевой нагрузки не нужно).
- **Postgres** (локально используется 17). Лучше в том же регионе, что и приложение: каждое действие игрока — это транзакция из нескольких запросов.
- **HTTPS** (токен игрока передаётся при подключении). Хостинги дают его сами; WebSocket идёт через тот же адрес (`wss`).
- Проверка здоровья: `GET /readyz` (200, если база отвечает), `GET /healthz` (процесс жив).
- Миграции базы применяются автоматически при старте.

Условия бесплатных тарифов меняются, перед выбором проверьте: засыпает ли приложение при простое, лимит соединений и объём базы, исходящий трафик, поддержку WebSocket. Если приложение засыпает, партии не теряются (состояние в базе), но игроки на время отключаются.

## Переменные окружения
Все необязательны (см. `.env.example`).

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `PORT`, `HOST` | `3000`, `0.0.0.0` | где слушать |
| `NODE_ENV` | — | `production` на хостинге (включает доверие к прокси и спокойные логи) |
| `DATABASE_URL` | локальная база | строка подключения |
| `DATABASE_SSL` | `false` | `true` / `no-verify` для управляемых баз с TLS |
| `PG_POOL_MAX` | `10` | размер пула; **не больше лимита соединений вашего тарифа базы** |
| `TRUST_PROXY` | `true` в production | видеть настоящий IP за прокси (нужно для лимита новых игроков) |
| `CORS_ORIGIN` | пусто | только если клиент и сервер на разных доменах (и тогда при сборке клиента задайте `VITE_SERVER_URL`) |
| `MAX_ROOMS` | `60` | потолок числа комнат (при превышении создание отклоняется с понятным сообщением) |
| `MAX_CONNECTIONS` | `400` | потолок одновременных соединений |
| `SOCKET_EVENTS_PER_SEC` | `15` | лимит событий в секунду на соединение |
| `SESSIONS_PER_HOUR_PER_IP` | `30` | новых игроков в час с одного адреса |
| `ROOM_TTL_HOURS` | `72` | комнаты без действий дольше этого срока удаляются |

## Выдержит ли 20 партий и 100 пользователей
Измерено на модели игры (карта из 35 клеток суши, 4 игрока, флот и по 6 юнитов у каждого):

| Показатель | Значение |
|---|---|
| Снимок состояния для одного игрока (CPU) | **≈ 0,4 мс** (после оптимизации; было 1,4 мс) |
| Размер снимка | ≈ 7 КБ, **≈ 0,9 КБ** после сжатия |
| Состояние партии в базе | ≈ 11 КБ |
| Применение действия (логика) | доли миллисекунды |

Расчёт для 20 партий × 5 участников и **1 действии в секунду на партию** (в пошаговой игре обычно реже):
- процессор: 20 × 5 снимков × 0,4 мс ≈ 40 мс в секунду, то есть порядка 4% одного ядра;
- база: ≈ 100 запросов в секунду; при задержке до базы 30 мс транзакция занимает соединение около 150 мс, поэтому 10 соединений дают ≈ 65 транзакций в секунду (нужно 20), а 5 соединений ≈ 30;
- трафик: ≈ 90 КБ/с со сжатием (≈ 320 МБ в час), без сжатия было бы ≈ 700 КБ/с. Сжатие Socket.IO включено.

Вывод: логика не узкое место, ограничивать будут **задержка до базы** и **лимиты бесплатных тарифов** (соединения с базой, трафик, сон при простое). Действия одной комнаты выполняются по очереди (блокировка строки), для пошаговой игры это безопасно и незаметно.

**Что не проверялось:** нагрузочный тест с реальными сокетами и удалённой базой (в среде разработки нет сети). Цифры получены замером логики и расчётом; после первого развёртывания полезно прогнать 3–4 партии вживую и посмотреть логи.

## Защита и эксплуатация
Есть: случайные токены игроков, лимит новых игроков с адреса, лимит событий на соединение, потолки комнат и соединений, ограничение размера сообщений и тела запроса, проверка всех входных данных (zod), заголовки безопасности, корректная остановка по `SIGTERM`, автоочистка старых комнат (раз в час).

Нет: паролей и почты (игрок анонимен: потерял токен в браузере, потерял личность), капчи, горизонтального масштабирования. Таблица игроков не чистится (записи маленькие).

Логи пишутся в JSON (pino); уровень задаётся `LOG_LEVEL`.
